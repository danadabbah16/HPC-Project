# HPC implementation and GPU results

## Experimental methodology

All experiments used the PyTorch 1D CNN, a batch size of 64, learning rate
`0.001`, seed `42`, and 10 training epochs. The input was one 30-second
`EEG Fpz-Cz` epoch sampled at 100 Hz. Training used inverse-frequency class
weights and the subject-based train/validation/test split described in
[`DATA.md`](./DATA.md).

The benchmark was executed on the SciTech cluster through Slurm. CPU runs used
one process with 1, 2, 4, 8, or 16 PyTorch threads. GPU runs used one NVIDIA
RTX 6000 Ada GPU on node `haskell`, with PyTorch 2.8.0 and CUDA 12.8 in the
cluster Apptainer container. The FP32 and AMP runs used the same model,
dataset, seed, batch size, learning rate, and number of epochs.

The downloaded Sleep-EDF data contained 147 PSG recordings. Five PSG files
had no matching hypnogram, so they were skipped. The final benchmark therefore
used 142 paired recordings: 127,220 training epochs, 25,306 validation epochs,
and 27,413 test epochs.

## CPU thread scaling

Speedup is measured relative to the 1-thread run:

```text
speedup = 1-thread training time / run training time
efficiency = speedup / thread count
```

| Threads | Training time (s) | Throughput (samples/s) | Speedup | Efficiency | Test accuracy | Macro F1 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 490.73 | 2,592.5 | 1.00x | 100.0% | 0.7523 | 0.7108 |
| 2 | 502.32 | 2,532.7 | 0.98x | 48.8% | 0.7461 | 0.7058 |
| 4 | 319.77 | 3,978.5 | 1.53x | 38.4% | 0.7529 | 0.7102 |
| 8 | 234.27 | 5,430.6 | 2.09x | 26.2% | 0.7507 | 0.7078 |
| 16 | 208.71 | 6,095.5 | 2.35x | 14.7% | 0.7494 | 0.7065 |

Increasing the number of CPU threads improved throughput and reduced training
time, but scaling was sublinear. The 16-thread run was only 2.35 times faster
than the 1-thread run, giving 14.7% parallel efficiency. The 2-thread result
was slightly slower than the 1-thread result, showing that parallel overhead
can outweigh the benefit at small thread counts for this workload.

Model quality was stable across the CPU runs. Test accuracy remained between
0.7461 and 0.7529, while macro F1 remained between 0.7058 and 0.7108. This
indicates that the resource configuration changed execution time rather than
the final classification behavior.

## GPU and mixed-precision comparison

| Configuration | Training time (s) | Throughput (samples/s) | Speedup vs CPU-1 | Test accuracy | Macro F1 |
|---|---:|---:|---:|---:|---:|
| CPU, 1 thread, FP32 | 490.73 | 2,592.5 | 1.00x | 0.7523 | 0.7108 |
| CPU, 16 threads, FP32 | 208.71 | 6,095.5 | 2.35x | 0.7494 | 0.7065 |
| RTX 6000 Ada, FP32 | 334.19 | 3,806.8 | 1.47x | 0.7518 | 0.7008 |
| RTX 6000 Ada, AMP FP16 | 425.56 | 2,989.5 | 1.15x | 0.7514 | 0.7014 |

The single GPU was faster than the one-thread CPU baseline, but it was slower
than the 16-thread CPU run. Mixed precision preserved accuracy and macro F1,
but did not improve runtime: the AMP run was slower than the FP32 GPU run.
This suggests that the workload was not dominated by large FP32 matrix
operations. Data loading, host-to-device transfers, kernel launch overhead,
and evaluation time likely limited the benefit of AMP for this relatively
small 1D CNN and batch size.

The recorded GPU Slurm jobs completed successfully on `haskell`. End-to-end
Slurm elapsed times were approximately 8 minutes 6 seconds for FP32 and
10 minutes 5 seconds for AMP; these include startup and container overhead and
are distinct from the training times reported by the application.

## Per-class results

The representative runs produced the following test F1 scores:

| Configuration | W | N1 | N2 | N3 | REM |
|---|---:|---:|---:|---:|---:|
| CPU, 1 thread | 0.8993 | 0.4044 | 0.7701 | 0.7648 | 0.7156 |
| CPU, 16 threads | 0.9007 | 0.4021 | 0.7605 | 0.7535 | 0.7158 |
| GPU, FP32 | 0.8806 | 0.3903 | 0.7971 | 0.7284 | 0.7075 |
| GPU, AMP FP16 | 0.8881 | 0.3850 | 0.7852 | 0.7407 | 0.7081 |

N1 was consistently the weakest class, which agrees with its lower frequency
and its known difficulty in sleep staging. The hardware and precision changes
did not materially change this pattern.

## Reproducibility

The cleaned experiment data is stored in
[`gabriel_scaling_results.csv`](../results/gabriel_scaling_results.csv).
The plots are generated by
[`make_gabriel_plots.py`](../scripts/make_gabriel_plots.py) and stored in
[`docs/plots/`](./plots/). The main commands were:

```bash
bash slurm/cpu_thread_scaling.sh
sbatch slurm/gpu_sample.slurm
sbatch slurm/gpu_amp.slurm
```

The raw dataset and processed `.npz` files remain outside Git because they are
large and are recreated by the documented Sleep-EDF preparation workflow.

## Limitations and HPC conclusion

The comparison used one GPU and one CPU node configuration, not multi-node
distributed training. GPU timings had repeated observations with some
run-to-run variation, so the cleaned table selects one representative run for
the main comparison. A larger batch size, more data-loader workers, cached
storage format, or DDP may improve GPU utilization and should be investigated
by the relevant team members.

For this workload, CPU thread parallelism was the most effective measured
optimization: 16 threads achieved the highest throughput. CUDA FP32 provided a
useful speedup over one CPU thread, while AMP preserved model quality but was
not beneficial for runtime. The results provide a reproducible single-node
reference for future DDP and EuroHPC scale-up experiments.
